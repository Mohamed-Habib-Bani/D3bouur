# D3BOUUR — Project Context for Claude

*This file is auto-loaded at the start of every session in this project. Full detail lives in `ros2_ws/docs/D3BOUUR_Project_Handoff.md` and `ros2_ws/docs/D3BOUUR_Phase2_Power_System.md` — read those for anything this file doesn't cover.*

## What D3BOUUR is

An intelligent welcome/receptionist robot, built as a solo internship project ("Stage") for **AcaROBOTICS**, a company doing educational robotics and AI. Based on an official spec ("Cahier des charges"). Mission: greet visitors at events/trade shows/schools/businesses by detecting a person, identifying/tracking their face, starting a voice conversation, responding vocally, and moving autonomously. It's explicitly a **technology demonstration platform** — polish and live-demo reliability matter as much as raw capability.

Required behaviors: detect person → orient camera → greet → converse (STT/LLM/TTS) → move autonomously (obstacle avoidance, go-to-point, return-to-origin — SLAM/mapping and face recognition are optional per spec). Also required: Wi-Fi remote control (manual drive, e-stop, live camera feed) and an on-screen UI (company info, training catalog, events, contact form).

This is explicitly a **learning project**, not just "get it working" — the goal is for the project owner to genuinely understand ROS 2 and robotics by the end, built to a professional standard (solo builder, no team).

## Hardware setup — confirmed working

- **Compute**: Raspberry Pi 5 (8GB, + fan), Arduino UNO (2nd unit — original had a dead USB-serial chip and was replaced) + HW-130 motor shield (M1-M4 terminals + servo header)
- **Chassis**: custom wood body, fully assembled (Phase 3 essentially complete) — base box (wheels, battery, electronics) + neck + head (camera, screen, mic, speaker)
- **Motors**: 4× JGB37-520 DC (no encoders, confirmed 2-wire). Terminal map: M1=left-front, M2=right-front, M3=back-right, M4=left-back. **M1 and M3 spin physically backward** relative to M2/M4 — compensated in software (Arduino firmware), not by rewiring.
- **Sensors**: 6× ultrasonic, all wired and confirmed working. Final pins: Neck-Front=A4, Neck-Back=A5, Neck-Left=A0, Neck-Right=A1, Base-Left=A2, Base-Right=A3, shared Trigger=Pin 9. (Original Front/Back pins 2/13 were unreliable on this board — moved to A4/A5.)
- **Servo**: head servo (turns screen toward visitors), imprecise/time-based not angle-based. Powered directly from the XL4015's 5V output (not Arduino's own regulator — Arduino USB's ~500mA limit couldn't drive it), signal wire only on Arduino pin 10. Working.
- **Screen**: 10.1" Waveshare HDMI LCD, 1024x600 — **touch is broken**, mouse+keyboard used instead.
- **Camera**: identified as **V380 Pro** (consumer WiFi camera, not industrial RS485). Gating question resolved: firmware **does** support ONVIF (PTZ via `ContinuousMove`, port 8899 — non-standard, found via nmap) and RTSP (`rtsp://user:pass@ip:554/live/ch00_0`, carries H264 video + AAC 16kHz mono audio). PTZ pan/tilt and microphone recording both confirmed working against the real camera. **Correction to earlier assumption**: the "PTZ" is not a physically rotating turret — code comments in `room_sweep.py` (added while building the panorama-stitch feature) record that this camera's pan is a **digital sensor-crop pan**, not physical rotation; this is why `stitch_panorama()` had to switch from OpenCV's `PANORAMA` stitch mode (assumes a physically rotating camera, bundle-adjusts per-frame focal length/rotation) to `SCANS` mode (built for translated, not rotated, captures) to get panoramas to stitch reliably. Earlier docs (this file and the handoff doc) describe it as having "motorized pan-tilt" / "360° built-in rotation" — that language is now known to be inaccurate and needs correcting. **Speaker / two-way audio is NOT available** via ONVIF or RTSP on this camera — confirmed dead end, would require reverse-engineering a proprietary binary protocol (port 8089/8800, AES-encrypted, key embedded in the phone app's APK) — decision made to buy a separate USB speaker later instead of pursuing that. Code lives in `ros2_ws/src/onvif_camera/` (`ptz.py`, `mic.py`, `room_sweep.py`, `engage.py`, `example.py`, `requirements.txt`) — plain Python, not yet a ROS 2 node.
- **Pi↔Arduino link**: serial over USB at **9600 baud**, custom text protocol (`M:v1,v2,v3,v4` motors, `S:angle` servo, `X` stop, `D:...` sensor stream, one line per direction). Confirmed working end-to-end (Phase 4 milestone reached). Firmware source (previously missing from the repo entirely — see the open-questions note on this) now lives at `ros2_ws/src/d3bouur_arduino/d3bouur_arduino/d3bouur_arduino.ino`; also handles HC-05 Bluetooth manual-control (`F`/`B`/`L`/`R`/`S` single-character commands, driving the robot without the Pi) on the same `Serial` object.
- **Mic**: resolved — using the V380 Pro's built-in mic via RTSP audio track (confirmed working), no separate USB mic needed. **Speaker**: still pending — camera speaker is not accessible (confirmed dead end, see camera integration below), a separate USB speaker will be sourced later.

## The Pi 5 power blocker (current #1 hardware gap)

The Pi 5 needs genuine USB-C Power Delivery negotiation to boot properly and get full current (without it: 600mA cap, red LED, boot failures). The XL4015 buck converter **cannot do this** (it's a charging-style module, confirmed unstable under load) and is now repurposed to power only the servo+sensor branch. All locally available options (Waveshare UPS 1S/2S/4S — wrong cell-count topology for an assembled 3S pack; L298N — that's a motor driver, not a regulator; generic buck converters — none available; online ordering — not possible for the intern) have been ruled out.

**Final decision, needs to be sourced/ordered**: Geekworm RPi5-5V5A-PD (primary — wide 9-24V input, accepts the 11.1V LiPo directly, genuine PD 5V/5A out, ~$15-20). Backup: Yahboom PD Power Expansion Board. This is a **parts-availability blocker**, not a skill gap — flagged for discussion with the AcaROBOTICS supervisor about a sourcing/ordering channel.

**Current workaround**: a borrowed phone charger (intact USB-C cable, real PD) powers the Pi for all development work — fully legitimate for software progress, just not usable in the final assembled robot.

Related, smaller blocker: the **motor branch (HW-130 EXT_PWR) runs completely unfused** — the only available fuse (F1AL250V, 1A) is reserved for the servo/sensor branch since the motors alone draw >1A normally. A proper 3-5A fuse is still needed; until then, motor testing requires the mandatory manual precautions in the Phase 2 doc (continuity check every session, one motor at a time first, stay present with hand on the switch, thermal/visual inspection).

## Working style — how to collaborate on this project

- **Go slow, one step at a time.** Don't jump ahead or batch multiple steps — confirm each step works before moving to the next.
- **Explain everything in detail**: what we're doing, why, and how to actually do it. Specifically call out what the alternative options were and why this one was chosen, and what real engineers/professionals/hobbyists typically use for this exact problem — so choices can be judged against real-world practice, not just "it worked."
- **This is a learning project.** The goal is genuine understanding of ROS 2/robotics/the full stack, not just a working robot the owner can't explain. Built to a professional standard, not simplified for being a first-timer.
- **Never assume — verify.** Ask clarifying questions before big decisions, using concrete options over open-ended questions where possible. Verify hardware claims physically (photos, multimeter readings, labels) rather than trusting assumed specs — this has caught real issues before (battery voltage config, HW-130 being a shield not a separate board, screen connector type).
- **Safety-first on anything irreversible or hardware-related.** Stop and ask before BIOS changes, soldering/wiring, destructive commands, or touching partition tables. There has already been one real safety incident (a switch wiring mistake caused a dead short and visible smoke — root cause was an imprecise instruction; corrected rule: a switch only ever sits on the positive line, negative/ground runs straight through to common ground, never through a switch). Take this kind of caution seriously going forward, especially with the motor branch running unfused.
- **Test/compare before committing to a tool choice** when a decision is genuinely close, rather than picking from specs alone (e.g. the planned LLM comparison test).
